# HAL-134 Demo Tenant Setup and Pilot Demo Script

## Goal

Create a repeatable, production-safe demo tenant setup and pilot demo flow for Linear HAL-111.

This runbook is designed for controlled demos and onboarding conversations only. It must not modify real client production data.

## Target Audience

- Founder/operator running live demos
- Internal implementation team preparing pilot onboarding
- Early pilot stakeholders from sales, procurement, finance, and operations

## Current Release Context

- Core ERP MVP is signed off for controlled demo/onboarding.
- Security cleanup and hardening are complete (HAL-108/HAL-131).
- Authenticated production smoke is complete and passed (HAL-109/HAL-132).
- Migration baseline decision is complete (HAL-110/HAL-133).
- Production URL: https://halalzi-erp.vercel.app

Important operator note: production admin password was exposed in chat earlier. Rotate/change it before broader demos and before sharing demo access with any external party.

## Demo Tenant and Company Naming Convention

Use a dedicated demo company that is visibly isolated from real tenants.

- Company name format: DEMO <ClientLabel> <YYYYMM>
- Optional short code: DEMO-<CLIENT>-<YYMM>
- Demo emails: use dedicated internal-controlled inbox aliases only
- Demo records prefix:
  - Products: DEMO-SKU-xxxx
  - Vendors: DEMO-VENDOR-xxxx
  - Sales orders: DEMO-SO-xxxx
  - Purchase orders: DEMO-PO-xxxx
  - CRM leads/deals/tasks: DEMO-CRM-xxxx

Never reuse existing production client company records for demos.

## Demo Role Setup

Create minimum safe role personas inside the demo tenant.

- Demo Company Admin
  - Full module access for guided walkthrough
  - Can create users, roles, and master data
- Demo Sales Staff
  - Sales orders and CRM access
  - No user/role administration
- Demo Procurement Staff
  - Vendors and purchase order access
  - No finance administration
- Demo Finance Staff
  - Finance accounts, receivables, payables, report views
  - No user/role administration
- Demo Read-Only Auditor
  - Dashboard, audit logs, and exports only

Validate least-privilege boundaries by confirming disallowed paths return 403 where expected.

## Safe Demo Data Rules

- Do not copy real customer PII into demo tenant data.
- Do not connect demo tenant to external client integrations.
- Keep all demo data synthetic, generic, and reversible.
- Label all demo records with DEMO- prefixes.
- Keep demo users separate from real client users.
- Never print secrets in logs, docs, screenshots, or tickets.
- Never commit local env files or credentials.

## Recommended Demo Dataset

Prepare realistic but synthetic sample data.

- Products: 20-40 active products, mixed categories, low-stock examples
- Vendors: 6-12 vendors with basic contact fields
- Purchase orders: 8-15 records across draft/ordered/received/cancel states
- Sales orders: 10-20 records across draft/confirmed/cancel states
- Finance accounts: core chart (cash, receivable, payable, revenue, expense)
- Receivables: 6-12 open/settled items with due-date spread
- Payables: 6-12 open/settled items with due-date spread
- CRM leads/deals/tasks: 12-25 mixed pipeline and follow-up tasks

## Pilot Demo Script (Step-by-Step)

Estimated duration: 35-50 minutes.

### 1) Auth/Login (3-5 min)

- Open production URL.
- Login using demo admin user only.
- Confirm post-login redirect to dashboard.
- Mention tenant isolation and role-based access model.

### 2) Dashboard Overview (4-6 min)

- Show top-level operational counters.
- Explain cross-module summary blocks (users, products, sales, procurement, finance).
- Confirm no sensitive auth fields are displayed.

### 3) Products and Stock (4-6 min)

- Open product list and highlight DEMO-SKU naming.
- Show stock levels and low-stock examples.
- Open stock ledger view to explain traceability of inventory movement.

### 4) Sales Flow: Confirm and Cancel (5-7 min)

- Create or open a DEMO sales order.
- Confirm order path and resulting state.
- Show cancel flow on a separate demo order.
- Explain that finance linkage updates are generated by workflow state.

### 5) Procurement Flow: Receive and Cancel (5-7 min)

- Open a DEMO purchase order.
- Show ordered to received transition.
- Demonstrate cancel on another demo PO.
- Explain inventory and finance effect at operational level.

### 6) Finance Flow: Receivable, Payable, Report View (5-7 min)

- Open receivables and payables lists.
- Show due-date and status behavior.
- Open finance report/dashboard view for summary checks.
- Keep explanation focused on safe operational reporting, not custom accounting advice.

### 7) CRM Overview (3-5 min)

- Show leads/deals/tasks pipeline.
- Demonstrate next-action tracking and owner assignment.
- Position CRM as MVP-phase operational workflow.

### 8) Audit and Export (3-5 min)

- Open audit logs and explain accountability trail.
- Show export path for operational reporting.
- Confirm that sensitive hashes/tokens/password fields are not exposed.

## What Not to Demo Yet

- Any workflow needing real client data migration/import from live systems
- Any feature not yet stable in roadmap notes
- Any destructive bulk operation
- Any operation requiring exposure of secrets
- Any unverified email/domain-dependent promises beyond current readiness

## Demo Reset and Cleanup Rules

- Disable or rotate demo credentials after external demo rounds.
- Archive or relabel stale demo records.
- Keep demo tenant isolated; do not merge demo records into client tenants.
- Review audit logs after each demo session.
- If tenant reset is needed, prefer manual scoped cleanup with explicit company filtering.
- Do not run destructive or cross-tenant cleanup scripts.

## Security Checklist Before and After Demo

Before demo:

- Confirm rotated production admin credentials.
- Confirm only demo users are used in session.
- Confirm no secret values are present in terminal history screenshots.
- Confirm smoke checks are green for current deployment.

After demo:

- Re-check audit logs for demo session actions.
- Disable temporary demo users not needed.
- Capture issues without including secrets or tenant-sensitive internals.
- Record demo date, audience type, and outcome.
